# Plan 0.2.0 E: move originals to the Recycle Bin after a verified compression

Part E of [0.2.0](0.2.0.md). This is an app feature with no format impact. It removes the user's files, so every
rule below exists to make data loss impossible. When in doubt, keep the file and say why in the job log.

## The setting

- **Category:** Compression. Label: *After a verified compression, move the originals to the Recycle Bin*. Off by
  default.
- **Warning when turned on:** "Osmium moves the files it compressed to the Recycle Bin after the archive is written
  and every block is verified. Files that were not compressed, and drives without a Recycle Bin, are never touched."
- It applies to every compress job (Compress page, Explorer verbs, watch folders), using the settings in effect when
  the job started.

## When the originals move (all must hold, checked after the archive is complete)

1. The job completed: no exception, not canceled.
2. Block verification was on for this job (`Compression.VerifyBlocks`). If it was off, nothing moves, and the log
   says why.
3. The archive builder reported no warnings (unreadable, skipped or changed files), and the archive file exists
   with the size the builder reported.
4. Each input the user gave (a file or a folder) is judged on its own:
   - **File:** it is in the archive, and its size and last-write time are unchanged since the scan.
   - **Folder:** a fresh enumeration that includes hidden, system and excluded files finds exactly the files that
     were archived (same relative paths, sizes and last-write times) and nothing else but folders. It contains no
     reparse points (junctions, symbolic links, OneDrive placeholders), and the archive is not inside it. Then the
     folder moves as one item, which can be restored as one.
   - Otherwise that input stays where it is, and the log names the reason: a file that was not archived (excluded,
     hidden), a changed file, a link, or the archive inside it.
5. The input is on a fixed local drive (`GetDriveType` = `DRIVE_FIXED`). Removable and network drives have no
   Recycle Bin, so files there would be deleted for good.

## How they move

- Use `IFileOperation` with `FOFX_RECYCLEONDELETE | FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT |
  FOF_NOERRORUI`, plus an `IFileOperationProgressSink` whose `PreDeleteItem` **refuses any item that the shell would
  not recycle** (its flags lack `TSF_DELETE_RECYCLE_IF_POSSIBLE`), so nothing is ever deleted permanently. Volumes set
  to "Don't move files to the Recycle Bin", and items larger than the Recycle Bin, are therefore refused rather than
  destroyed.
- One operation per job. Its result is logged per input: `moved to the Recycle Bin: <path>` or
  `kept <path>: <reason>`. Any failure keeps the remaining files, and the job stays *Completed* (the archive is
  good) with a warning.
- The job's summary and the tray notification say how many inputs were moved and how many were kept.

## Tests

- **Desktop (Linux, fake recycler and drive query)**, every rule in both directions:
  - verification off;
  - builder warnings;
  - a canceled or failed job;
  - an excluded or hidden file inside a folder;
  - a file changed after the scan;
  - a link inside a folder;
  - the archive inside an input folder;
  - a non-fixed drive;
  - mixed inputs, where some move and some are kept;
  - nothing moved when the setting is off.
- **Windows (UI self-test on CI):** compress a temporary folder with the setting on, then check that the folder is
  gone and the recycler reported it as recycled. Also check that a folder holding an excluded file is kept. (The
  runner's Recycle Bin is discarded with the machine.)
