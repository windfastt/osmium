# Plan: Osmium 0.2.0, part B — compressor

Part B continues the measured gaps from the 0.1.1 benchmarks ([BENCHMARKS.md](../BENCHMARKS.md)): issue #1, Osmium CM
against ZPAQ on x86 code, and issue #2, the cost of the parameter search. It starts once part A's golden vectors pin
today's `cm` and filter output. Part A also adds the "needs a newer Osmium" message for archives that use methods a
reader does not know.

## Versioning decision: a new method, `cm2`

The CM stream has no version byte. Every parameter is always serialized, so adding a parameter breaks every CM block
for 0.1.x readers. Changing shared code paths (counters, mixer, APMs) would change the output of existing archives.
Therefore:

- `cm` (method id 7) is **frozen**. Part A's golden vectors pin every model set and parameter.
- `cm2` (method id 8) is a copy of `cm` that is free to change until 0.2.0 is released, then frozen and pinned by its
  own golden vectors. 0.1.x readers get a clean "needs a newer version" error per block.
- Planner, candidates, settings and the decode-speed estimate treat `cm2` like `cm`; CM-specific checks match either
  id. The engine fingerprint changes, as it does with any assembly version bump, so 0.1.x and 0.2.0 workers refuse each
  other.

## Workstreams

### E1 — `cm2` with x86-aware modelling (issue #1)

**Owns:** `src/Osmium.Core/Codecs/Cm2/**` (new), the `MethodRegistry` registration line, and the CodeX86 /
CodeArm64 / Binary entries in `Candidates.cs`.

Candidate improvements, each measured with `osmium lab` on the program-files corpus and the mixed corpus before it is
kept:

1. **x86 contexts.** Model the opcode byte, the ModRM byte with the opcode, the previous instruction's opcode, and the
   operand position. Track the instruction boundary with a light length decoder, or with the E8/E9-aligned heuristic
   used by paq-style exe models.
2. **Bit-history state machines** instead of plain probability counters, at least for the high orders.
3. **An order-2 APM, and an APM keyed by match length.**
4. **A two-layer mixer:** several neurons selected by order-0 / order-1 / match state / x86 state, feeding a final
   mixer.
5. **Sparse and word models gated per class.** Binary only, x86 only.

**Target:** close a measurable part of the 6.2 % gap to ZPAQ -m5 on program files. Do not get bigger on the mixed
folder. Report the speed change; a modest slowdown is acceptable for Ultra/Insane, but not more than 1.5×.

### E2 — Parameter-search screening (issue #2)

**Owns:** `Planner.cs` (`ChooseAsync`, `HillClimbAsync`) and `Profiles.cs`.

- Keep the previous rung's sample and its scores.
- Run each search step's neighbours on that smaller sample first.
- Promote the best `max(2, ceil(n/Eta))`, and only those within +0.5 % of the incumbent, to the full sample.
- Accept a neighbour only if it beats the incumbent on the full sample.
- Count screened neighbours against `SearchEvals`.
- Groups without a smaller rung behave as today.

The fake `ITrialRunner` tests from part A must keep passing, plus new tests for the screening.

**Target:** archive sizes within 0.2 % of 0.1.x on both corpora, and lower planning time.

### E3 — x86 filter v2 (optional; only if E1 measurements show the filter is the bottleneck)

Add a new filter id (71): E8/E9 plus Jcc (0F 8x) conversion, with an exhaustive invertibility test like
`X86FilterSurvivesExhaustiveShortPatterns`. The planner's "natural filter" check must not stack it on top of `x86`.

### E4 — Benchmarks, documentation and site

- Re-run `tools/crosscheck.py` on the corpora built by `tools/bench/`, and add `docs/benchmarks-0.2.0.json`.
- Regenerate `docs/index.html` with `tools/site/build.py`.
- Update BENCHMARKS, IMPROVISATION §5, ROADMAP, CHANGELOG and FORMAT (`cm2`).
