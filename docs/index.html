As small asyou have time for.

Osmium lives in the notification area and packs files into .osa archives. It works out what each file is, gives every kind of data its own pipeline, races codecs on samples and tunes their settings. Give it more time and it brings in context mixing and the other PCs on your network.

Benchmarks · 2 folders · 8 other tools in 9 settings · every archive unpacked and compared

Smallest on mixed data

Each tool compressed the same two folders at the strongest setting people commonly use, and every archive was unpacked and compared with the original, file by file. On the mixed folder Osmium is the smallest; on a folder of program files, ZPAQ and lrzip still are. Bars show the archive size as a share of the original; shorter is better.

How it was measured

Stream compressors got a tar of the folder. 7-Zip, ZPAQ, zip and Osmium archived the folder directly. xz and Zstandard ran single-threaded, because their multi-threaded modes split the input and lose ratio.

Where Osmium loses

On program files, ZPAQ -m5 and lrzip beat Ultra: their models for x86 code are stronger than Osmium's today, and closing that gap is next on the list. Max only matches xz on machine code, since both are LZMA with a branch filter, and Fast is larger than zip on the mixed folder.

The cost of the smallest file

Context mixing decompresses about as slowly as it compresses. Osmium shows the expected extraction time and memory before it starts, and Max keeps LZMA's fast extraction.

How it works · nine stages · every decision written to the archive's planner log

It reads the files before it packs them

Most archivers run one algorithm over everything. Osmium sorts files by what they contain and plans each group separately, then proves every block decodes before it writes anything.

Scan

Walks the inputs, applies exclude patterns, reads sizes and timestamps.

Analyze

Signatures (PE, ELF, WAV, BMP, PNG…), entropy, a zstd-1 probe and record stride.

Rules

Your per-file patches and rules force, forbid or tune pipelines.

Dedup

Identical files are stored once. Insane also finds repeated chunks inside and across files.

Group

Files with the same kind of data share solid blocks, aligned to their record size.

Plan

Candidates race on growing samples; the losers drop out at each round, then the winner's parameters are hill-climbed.

Compress

Blocks run in parallel inside a memory budget, on this PC or on paired workers.

Verify

Every block is decoded and compared byte for byte before it is written.

Commit

Frames are written in order, the archive is read back, then renamed into place.

Write the pipeline

Filters, then one codec, with any parameter you want to pin.

# 12-byte records: delta per field, then LZMA
osmium a out.osa data ^
  --pipeline "delta(stride=12)+lzma(dict=128M,lc=0,lp=2,pb=2)"

# x64 code: branch converter, then context mixing
x86+cm(mem=24,models=4095)

# 16-bit stereo WAV: predictor after the 44-byte header, then CM
pcm16(offset=44,channels=2,lms=32)+cm

Borrow the other PCs in the house

Insane spends most of its time racing pipelines. Pair a few idle machines and the trials and the heavy blocks spread across them, while your PC keeps the final say.

  • Workers authenticate with the shared key (mutual HMAC over an ECDH handshake) and must run the same engine version.
  • They see the contents of the blocks they compress, never file names. Pair only machines you trust.
  • Every remote result is decoded and compared on your PC. A worker that returns a wrong result is quarantined.

  1. Make a key once

    Share the OSM1-… key with the machines you want to pair.

    osmium keygen

  2. Start a worker on each helper

    Or use Lend this PC to the cluster in its tray menu.

    osmium worker --key OSM1-…

  3. Compress with workers

    Workers on the network are found automatically.

    osmium a big.osa D:\data --profile insane ^
  --workers auto --cluster-key OSM1-…

Safety · .osa format 1.0 · XXH128 per block and file · CRC32 per frame header

Nothing is written until it has been read back

Smaller files are worthless if they do not come back intact. Each block is decoded and compared before it reaches the disk, and the finished archive is read again before it replaces anything.

HeaderMagic, format version, TLV extensions, CRC32
OBLK framePipeline descriptor, sizes, XXH128 of the raw data, XXH3 of the payload
OBLK frameOne per solid block, in plan order
···
IndexFiles, folders, timestamps, per-file hashes, dedup segments. Encrypted, names included, when a password is set
OSAEFooter: index offset and length

Layout of an .osa file, not to scale. Every frame header carries its own magic, number and CRC, so damage is reported block by block and never decoded silently.

Verified before written

Every block is decoded and compared with its input. A remote worker's block is checked the same way.

Atomic and change-aware

Archives are written to a temporary file, re-read, then renamed into place. A file that changes while it is read is detected.

Encrypted, names too

AES-256-GCM with PBKDF2-SHA512 and HKDF. With a password, file names, pipelines and contents are encrypted; only the block count and block sizes stay visible.

Safe extraction

Paths that try to leave the target folder are refused, and the Mark of the Web is carried over to extracted files.

Same output everywhere

The context-mixing codec is integer-only. CI checks a golden hash on Linux and Windows.

Extraction cost up front

Before and after compressing, Osmium tells you how long extraction will take and how much memory it needs.

Roadmap · after 0.1.1 · measured gaps first

What comes next

The benchmarks above show where Osmium still loses. Those gaps come first; everything else waits until it has a prototype and a number.

Next

Beat ZPAQ on program files

On 124 MiB of Windows DLLs and EXEs, ZPAQ -m5 is 6.2 % smaller than Ultra. Osmium CM needs stronger models for x86 code: E8/E9 limited to PE code sections, bit-history counters, a two-layer mixer, and opcode and ModRM contexts.

ZPAQ -m525.6 %
lrzip -z26.5 %
Osmium Ultra27.3 %
xz -9e28.8 %

Done when the gap shrinks measurably without losing ground on the mixed folder, and the codec stays integer-only and deterministic.

Next

Faster planning for Ultra and Insane

Ultra spends 292 of its 346 seconds on the mixed folder planning, mostly trying parameter variations on the largest sample. The search earns its keep, shrinking each group by 2–8 %, so it stays.

The plan: try each variation on the previous, smaller sample first and send only the best few to the full sample. Insane, whose largest sample is 16 MiB, gains the most.

Done when plans stay deterministic, sizes stay within about 0.2 %, and planning time drops.

Planned

  • Recompress compressed files. Bit-exact re-deflate for PNG, ZIP, DOCX and PDF, and lossless JPEG recompression. Today they are stored as-is.
  • Repair and grow archives. osmium salvage, recovery records, append and update, multi-volume.
  • Deeper Windows integration. A top-level Windows 11 context menu and notifications with actions.
  • Signed builds, so SmartScreen stops warning.

Exploring

  • Faster context mixing. Integer SIMD inner loops, aiming for 1.5–2× with identical output.
  • Smarter grouping. Similar files next to each other, and different pipelines for regions of one file.
  • Cluster. Passphrase pairing, IPv6 discovery, a second worker double-checking context-mixing blocks.

The full list, with definitions of done: ROADMAP.md.
